# 0004 — Provider-agnostic authentication with application-owned user ids

**Status:** accepted

## Context

The platform will eventually authenticate through a hosted provider — Clerk,
Auth0, Firebase, Cognito, or any OIDC issuer. Which one is not yet decided, and
it may change.

Two failure modes are common and expensive to undo:

1. The provider's subject id becomes the application's user id, so migrating
   providers means rewriting every foreign key.
2. Provider-specific concepts (organisations, claims, session shapes) spread
   through the domain, so the provider cannot be swapped at all.

Local development must also work with no provider account.

## Decision

**An interface, not a dependency.** `AuthProvider.verifyToken(token)` returns a
normalised `AuthIdentity` or `null`. Everything downstream — middleware,
services, repositories — depends only on that interface.

**Application-owned ids.** `users.id` is generated by this application.
Provider credentials live in `user_identities` as `(provider,
provider_user_id)`, unique together. One user may hold several identities, which
is what makes provider migration and account linking possible.

**Nothing provider-specific escapes.** `AuthIdentity` carries `provider`,
`providerUserId`, `email`, `displayName` — and deliberately no raw claims and no
application user id. Mapping an identity to a user is a persistence concern.

**A local provider, always available.** `AUTH_PROVIDER=local` verifies JWTs this
repository signs itself, with HS256 pinned and issuer and audience checked. No
external account is needed to run or test the stack.

**Stateless verification.** No server-side session is consulted, so any API
replica can serve any request — a precondition for the load balancing in ADR
0005.

## Consequences

- Adding a hosted provider means writing an adapter and extending one enum. An
  exhaustiveness guard in the factory turns a missing adapter into a compile
  error.
- The extra indirection costs a join to resolve an identity to a user. That is
  the price of being able to change providers at all.
- `issueLocalToken()` exists for development and tests only. It is exported from
  a server-only package and has no hosted counterpart.
- As of the bootstrap the API resolves an identity per request but **nothing
  requires it**: no procedure is protected and no identity is mapped to a `users`
  row. Those are Milestone 2 Issues; the schema and the abstraction exist so
  that work is additive rather than a redesign.
